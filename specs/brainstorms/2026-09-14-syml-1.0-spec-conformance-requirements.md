# syml 1.0: Full Conformance to the SYML Specification

## Problem Frame

`syml` 0.6.2 on PyPI predates `SYML-SPECIFICATION.md`. The spec text currently
labelled "v1.1" is the 1.0 spec (the "1.1" label only records that it went
through one review pass); no conforming implementation exists. An empirical
audit on 2026-09-14 ran every ```syml block in the spec that states an Output
or ERROR through the current parser: **27 of 53 pass, 26 fail**, across 21
verified gaps. Library 1.0.0 is the release where the implementation matches
the spec in full, including the serializer, and the spec is relabelled 1.0 to
match. Users of 0.6.2 get a documented clean break.

The audit's full gap list, with a repro for every item, is committed beside this
document as `2026-09-14-syml-1.0-spec-conformance-audit.md`.
`todo.txt` is written against spec v1.0 and is partly stale; see Key Decisions.

## Requirements

**Parsing conformance (spec §4–§9)**

- R1. Every ```syml block in the spec that states an Output produces exactly that
  output from `loads`; every block that states an ERROR raises the named error.
- R2. Pre-processing per §9.0: a single leading BOM is stripped, CRLF and bare CR
  become LF, a BOM-only document is the empty document, and a tab anywhere in
  the leading indentation of a non-blank line raises `TabIndentationError`
  (D14; whitespace-only lines are blank and discarded first). A tab after `key:` or
  `-` is value content, never separator whitespace (D5).
- R3. Line splitting per §13.3: only U+000A separates lines; U+2028, U+0085,
  U+000B, U+000C and friends never do.
- R4. Structural lines lex per the §4.1 grammar as printed: bare `-` takes a
  block value, `- ` is an empty list item, `key:value` and `-item` fall through
  to scalar text (§7.6), `key: ` equals `key:` (D6), whitespace-only lines are
  blank and never affect indentation (B1), and keys exclude the Unicode
  `White_Space` set and control characters (D15, A5).
- R5. Empty values, empty documents, and comment-only documents yield `""`,
  never `None` (§7.3, §7.4, §11.1).
- R6. Tree building per §9.3/§5.3: siblings match on exact indentation (`==`,
  B4); a key-value or list item that already has a child is closed; a
  multiline value has a baseline set by its first own-line (D11), preserves
  indentation beyond it, ends on a shallower line which is re-offered up the
  tree (B5); plain text at a container's level is an error (M24); an inline
  key after `- ` sets the sibling column (M23); blank and comment lines inside
  a value are skipped (D12); a continuation-position line that lexes as
  structure is structure (D13).
- R7. Duplicate keys in a mapping raise `DuplicateKeyError` at incorporation
  time, comparing keys by code point (B6, M16).
- R8. Quoted strings per §4.7 and D2/D3: recognised only inline after `key:` or
  `- `; single-quoted with `''` escape; double-quoted with the §4.7 escape set;
  a quoted value ends its line and is complete (no continuation); unterminated
  quotes, trailing text after the closing quote, invalid escapes, surrogate
  code points and code points above U+10FFFF raise `MalformedQuotedStringError`.
  Bare lines never quote-decode.

**Error taxonomy and API (spec §11)**

- R9. `syml` exports `ParseError`, `OutOfContextNodeError`, `DuplicateKeyError`,
  `TabIndentationError`, `MalformedQuotedStringError`, `UnrepresentableValueError`,
  and a new `EncodingError` (for R10; the spec's §11.3 gains it, since the spec
  is open) with the inheritance §11.3 states. No Parsimonious
  exception ever escapes `loads`/`load`. Every `ParseError` exposes `.message`,
  `.position`, and `.line_text` as named attributes.
- R10. `load()` accepts either a text stream or a binary stream. Binary input is
  decoded as strict UTF-8 and invalid bytes raise `EncodingError` (M13).
- R11. `dumps(value)` / `dump(value, fp)` exist and follow §11.2: the quoting
  table in §11.2.1, exactly one space after `-`, no block continuation for
  embedded newlines, insertion-order keys (D8), and `UnrepresentableValueError`
  for empty list, empty mapping, unrepresentable keys (D1, M8) and root scalars
  per §11.2.4 (D17). `loads(dumps(x)) == x` for every representable `x`.

**Source tracking (spec §10)**

- R12. `as_source()`, `Source`, and `Pos` are a supported, documented, fully
  tested 1.0 surface; the `# pragma: nocover` blanket over `nodes.py` is
  removed.
- R13. `Pos` index, line, and column refer to the caller's **original** text,
  before BOM stripping and CRLF/CR normalisation, so editor integrations can
  point at the real character.

**Release**

- R14. `pyproject.toml` version becomes `1.0.0`; the spec header is relabelled
  "Version 1.0" with a status line naming `syml` 1.0.0 as the conforming
  reference implementation; `SYML-SPEC-REVIEW.md`'s subject line and the
  constitution's principle IV are updated to match.
- R15. A migration section (CHANGELOG or README) lists every user-visible
  behaviour change from 0.6.2: `None` → `""`, tabs and duplicate keys become
  errors, quotes decode (and `'Tis`-style inline values become errors), leading
  `-`/`key:value` fallthrough, Parsimonious exceptions no longer leak, new
  `load()` input types, new `dumps`/`dump`.
- R16. `todo.txt` is retired or rewritten so the repo has one conformance
  ledger; CLAUDE.md's "Spec vs. implementation" section is rewritten to say the
  parser conforms.
- R17. Hygiene: `tests/test_nodes.py` is populated (the untracked `.orig` is
  folded in or deleted), the dead `return` in `basetypes.Source.__add__` is
  removed, and importing `syml` emits no `SyntaxWarning`.

## Success Criteria

- Every spec example with a stated Output or ERROR runs as an automated
  acceptance scenario and passes (53 today; the count tracks the spec).
- The D1–D17 probe inputs from the review's verification record (quoted
  continuation, blank line in value, tab-only line, `-   name:` spacing,
  surrogate pair, NBSP in key, U+2028 in a value) all behave as the spec says.
- `uv run pytest`, `just acceptance`, mypy strict, ruff, and the 100% coverage
  gate all pass with no `# pragma: nocover` beyond what constitution III permits
  (provably unreachable branches only).
- A 0.6.2 user reading the migration notes can predict every behaviour change
  they will hit.

## Scope Boundaries

- **§13.4 implementation limits are deferred** (depth, line length, document
  size, `DocumentLimitError`). The deep-nesting `RecursionError` (500+ levels
  today) stays and is documented as a known limitation; the spec's §11.3 class
  list and §13.4 are edited to mark limits as post-1.0.
- No v1.2 syntax: no `[]`/`{}` empty-collection tokens, no quoted keys, no
  surrogate-pair combining, no post-marker-tab error. Values needing them stay
  unrepresentable and `dumps` raises.
- No root-scalar quoting (D17 stands).
- No deprecation/bridge release; no compatibility flags.

## Key Decisions

- **The spec text is the 1.0 spec**: relabel "v1.1" → "1.0" at release. The
  "1.1" label recorded a review pass, not a new language version. The spec's
  §14 version history folds the review pass into the single 1.0 entry rather
  than keeping two entries.
- **Full conformance including `dumps`**: a 1.0 that cannot round-trip is a
  half-conforming 1.0.
- **Keep D17**: no new grammar for root quoting; `dumps` raises instead.
- **Clean break from 0.6.2, documented**: 1.0 is the conventional place for
  breaks; a 0.7 bridge would add code that is deleted at 1.0.
- **Defer all §13.4 limits**: shipping speed over resource hardening for now.
- **Spec is open during implementation**: the implementer may edit spec text
  when implementation exposes a defect, without a prior decision gate. This
  relaxes constitution principle IV's "settle before implementing" clause for
  this feature; the constitution is amended under R14. Edits should still land
  in the same commit as the behaviour they change.
- **One feature, one epic**: "1.0 conformance" is specified as a single
  `/sp:02-specify` feature despite its size.
- **Source positions in original text** (R13) because editor use is the point
  of source tracking.
- **`load()` accepts text and binary streams** (R10) so `open(path)` callers
  keep working while strict UTF-8 is enforced where bytes are available.
- **todo.txt is superseded**: v1.1 decided its A1 open question
  (`MalformedQuotedStringError`), narrowed quoting to inline positions, moved
  tab detection to pre-processing with its own class, folded inconsistent
  indentation into `OutOfContextNodeError` (D7), replaced A9's baseline rule
  with D11, and made three "already conformant" items non-conformant (§6.4
  mixed content, §5.1/5.2 joining, §7.5 tab after colon).

## Dependencies / Assumptions

- Audit gap list (`2026-09-14-syml-1.0-spec-conformance-audit.md`), by area: grammar
  (quoted strings, `&eol` guards, `text = ~"[^\n]*"`, `indent = ~" *"`,
  `ws = ~" +"`, key class); tree builder (`==` siblings, closed nodes,
  baseline + re-offer, container-level text, `- ` column, duplicate keys);
  pre-processing (BOM, CRLF/CR, tab scan, line splitting); error taxonomy
  (5 missing classes, named attributes, Parsimonious leak); new API
  (`dumps`/`dump`, binary `load`); hygiene (test_nodes, dead code,
  SyntaxWarning, version string).
- The §4.1 grammar as printed loads in Parsimonious and parses all 54 spec
  blocks (review verification record); it can be transcribed rather than
  re-derived.
- The review's `v11_builder.py` (~150 lines, session scratchpad of the review,
  may not survive) implemented §9.0–9.4 literally and matched 45/45 examples;
  the tree-builder rewrite can follow that shape.

### Deferred to Planning

- [Affects R4][Technical] D15's `White_Space` set vs Python `re`'s `\s`
  (which also matches U+001C–U+001F) vs §4.1's key class excluding
  `\x00-\x1f`: which rule rejects `key\x1cname: v`, and as scalar fallthrough
  or error? Spec is open; settle and edit.
- [Affects R13][Technical] Mechanism for mapping normalised-text positions back
  to original positions (offset table vs parsing the original with a
  CR-tolerant grammar).
- [Affects R9][Technical] Exact attribute shape of `.position` (a `Pos`? line
  number?) and which errors carry `line_text`.
- [Affects R1][Needs research] Fixture strategy for examples with trailing
  spaces (`key: `, `- `, §7.5 preservation): the pre-commit
  `trailing-whitespace` hook strips them from files, so these must be built
  programmatically in tests.
- [Affects R11][Technical] Whether `dumps` output format for nested structures
  (indent width, blank lines between top-level keys) is fixed by the spec or
  an implementation choice to document.
- [Affects R12][Technical] Whether `Source` keys colliding on text
  (`Source.__eq__`/`__hash__` by text) needs any change now that duplicate
  keys are detected before materialisation (m4).
